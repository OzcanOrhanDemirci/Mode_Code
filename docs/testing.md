# How Mode_Code is tested

Mode_Code sits between an AI agent and your machine. A tool in that place has to be trusted, and trust has to be earned with evidence, not adjectives. This page describes every layer of testing, what each layer proves, what it cannot prove, and how to run it yourself. The numbers in it are produced by the test runs, not typed by hand.

## Principles

1. **A false alarm is a bug.** A safety belt that asks about harmless commands trains people to click "allow" without reading. Every protective rule is tested twice: it must catch what it is for, and it must stay silent on the harmless commands next to it.
2. **Test what ships.** Unit tests run the TypeScript source; a separate layer runs the built bundles (`dist/cli.mjs`, `dist/hook.mjs`, `dist/plugin`) the way Claude Code and a person run them.
3. **Every assumption is measured.** Where the code assumes something about the machine (how Git Bash spells `/tmp`, whether the file system ignores case, whether a folder is a link), that assumption is written down as a test that measures the real machine: in CI on Windows, Linux and macOS, and on your machine by `mode-code doctor`.
4. **Hermetic and harmless.** Tests never touch your real `~/.claude` or `~/.mode-code`, never open a network connection, and never execute the commands the belt judges. Belt samples are evaluated, not run.
5. **Deterministic.** No test depends on the clock, the locale, the terminal width or the order of files unless it sets them itself. Property tests use a recorded seed, so a failure can be replayed exactly.
6. **The tests are tested.** Mutation testing changes the code on purpose and checks that some test fails; a maintenance self-check breaks a sandbox on purpose and checks that the doctor finds and repairs every fault.
7. **Honest limits.** Each layer says what it does not cover. On native Windows the belt is an accident preventer, not a security boundary (see [safety-belt.md](safety-belt.md)).

## False alarms

The belt's job is to ask about the rare dangerous call and to stay out of the way for everything else. Two instruments keep it honest:

- **The everyday corpus** (`test/corpus/`): commands people and agents actually run, written by hand, grouped by ecosystem. Each must come back `allow` with no findings. A new rule that makes any of them ask fails the build.
- **Replay** (`mode-code belt replay [--days N]`): runs the belt over the shell and file tool calls in your own recent Claude Code sessions and prints counts only: how many calls, how many would have been asked about or blocked, by rule. Nothing is executed and no command text is printed. On the author's machine, 30 days and about 36,000 calls produce roughly four questions a day; the number is re-measured before each release.

## Self-protection

What the belt protects, and the spellings it must see through:

- its own data folder (`~/.mode-code`), hook program and plugin files;
- Claude Code's settings files, global config, plugin registry and managed settings;
- the memory folders the person registered;
- under every spelling: `C:\x`, `C:/x`, `/c/x`, `/cygdrive/c/x`, `\\?\C:\x`, `~`, `$HOME`, `%USERPROFILE%`, `$env:USERPROFILE`, relative paths, `..`, mixed case on Windows and macOS, Git Bash's `/tmp`, Windows 8.3 short names (`MODECO~1`), the trailing dots and spaces Windows drops from a name (`.claude.`), and protected folders that are themselves links (a dotfiles repository behind `~/.claude`).

And how it fails: a hook that crashes, cannot parse its input or runs past its deadline refuses changing tools (`Bash`, `PowerShell`, `Write`, `Edit`, …) and lets pure reads through, so a broken belt never silently opens and never locks the session.

## The maintenance check: `mode-code doctor`

`doctor` is the same set of checks the tests use, run on your machine. It groups them as **Node.js**, **Claude Code**, **installation**, **protection**, **shells and terminal**, **file system**, **git**, **data** and **self-tests**. Each check reports `ok`, `info`, `warn` or `fail` with the measured value behind it.

When a check fails and a safe repair exists, `doctor` offers it; `doctor --fix` applies them without asking. Every repair backs up what it changes, is re-checked right after (a repair counts only if the check then passes), and never weakens a protection: repairs only restore. What cannot be repaired automatically is reported with the exact next step.

When an agent runs `doctor`, the repairs that would put code or a program into the protection are refused and left to you: copying the hook program or the plugin files from the build that runs the doctor, reinstalling, updating or turning on the plugin, pointing the hooks at another Node.js, and rewriting your settings file. Hook entries are put back only with the Node.js you installed them with. Otherwise an agent could build a weaker hook and have the doctor install it for it. Housekeeping repairs (data folders, the session index, stale files, a broken quota reading, permissions) run either way.

`doctor` also runs the built-in self-tests: the samples the CI uses for the belt, the parsers, the secret scanner, the keywords and the footer, run against the code installed on your machine, and the installed hook program compared with the in-process belt on the same samples.

`doctor --self-check` tests the doctor itself: it builds a throwaway sandbox (temporary folders, a stand-in `claude`), breaks it in known ways (hooks removed, hook program altered, settings file broken, data folder missing, index corrupted, …), and verifies that every fault is detected and every repairable one is repaired. Your real files are not touched.

## Running the tests

```sh
npm run build          # first: the process tests also run the shipped bundles in dist/
npm test               # L1–L7 and L9: invariants, unit, properties, corpus, protection, processes, bundles, assumptions
npm run test:coverage  # the same, holding each file to its coverage floor (test/coverage-floors.json)
npm run test:mod       # L8, needs Claude Code on PATH (says "skipped" without it)
npm run test:mutation  # L11, about seventeen minutes on 12 threads
npm run test:live      # L10, opt-in, uses a little quota
npm run test:package   # L12, the package as npm installs it
npm run test:rename    # L13, the rename rehearsal
npm run test:installer # L14, the one-line installer in every shell this system has
npm run test:av        # L15, on Windows with an antivirus on (says "skipped" without one)
npm run verify         # every layer that can run here, one line each; --fast leaves out mutation, --live adds L10
```

A property test that fails prints its seed and the smallest input that fails; `TC_SEED=<seed> TC_RUNS=<runs> npm test` replays it exactly.

### What a task costs of the quota

`mode-code measure` ([quota.md](quota.md)) reads the transcripts and the quota readings on the computer and writes nothing: each session cut into tasks at its commits and pushes, each call priced and weighed by what the quota was measured to count, with the traces of how the work went. The pure part, `src/core/measure.ts`, is tested in `test/core/measure.test.ts`; the disk side in `test/node/measure.test.ts`. A change meant to save quota is compared with it as [quota.md](quota.md) describes, the cost and the traces together.

## What the tests found

Every one of these was a real defect in code that already had tests, found while building the layers above and fixed with a test that keeps it fixed:

- **Self-protection bypasses.** Windows 8.3 short names (`MODECO~1`) and trailing dots and spaces (`.claude./settings.json.`) reached protected files without being recognised; so did a protected folder reached through a link. The first fix for short names broke protection when the data folder itself was spelled short: the CI's Windows runner, whose temporary folder is `RUNNER~1`, caught it.
- **False alarms.** On macOS and Linux every recursive delete under the home folder was blocked, inside projects too (found while writing the macOS and Linux tests). Dry-run deployments were asked about (found by the corpus).
- **Missed calls.** `npx wrangler deploy` hid the program it runs from the belt (found by measuring the author's own sessions).
- **Crashes and inconsistencies.** A command containing `__proto__` or `constructor` crashed the parser; the width the screens measured differed from what Ink draws on 756 characters, emoji and symbols among them; a path whose last name trims to `.` or `..` resolved differently the second time (property tests, the last one only with 50,000 cases and a fresh seed).
- **Contracts.** `install --json` and `uninstall --json` printed text before the JSON (process tests).
- **The command classifier (modes).** Reviewing 297 command forms one by one found `sed` writing through `w` when the script was unquoted or followed an address, `awk -i inplace` taking the program for a file, `gawk -i` loading a library unseen, `go env -w` and `dpkg -i` taken for reads or local changes, `dd of=$VAR` read literally, and `wget -qO-` taken for a download into the folder. The property test found a program named `__proto__` crashing a table lookup, as the belt's had once.
- **The flows, in real sessions.** A report source that named its file first was refused when a later word on the line was in backticks; a verification line counted a note in backticks as a second command; a session started in Claude Code's plan mode was not known as one before its first prompt, so the plan went to the wrong file. Each was seen in a live or an interactive session and fixed with a test.
- **The test setup.** A live session started in a folder inside this repository, prompted with the keyword "continue", found the repository's uncommitted changes and committed them under its own messages (on the author's machine, 2026-10-13); the live sessions now work outside any repository, with a repository of their own, and the keyword session asks for a summary instead. On Windows, a prompt with a line break was cut where `cmd.exe` starts the session; the prompts carry none. An antivirus locked copies of a test file full of shell commands in the system's temporary folder, so the mutation workers moved into the repository's ignored `.tmp`. A test named "none skipped" made `verify` report the engine layer as skipped. On CI (Windows, Node.js 24) coverage measured one screen at 99.1% of its lines on some runs and at 74.7% and 71.7% on others, every test passing. The test that draws every screen at every width read the screen a fixed 80 ms after the first frame, but the screen asked for opens a frame later; on a loaded runner that frame came after the pause, the test checked the home screen instead and passed, and the tokens screen, drawn by no other test, never ran. The screens now have to open (the footer names their address) or the test fails; under a CPU load locally, 28 of 59 screens took longer than the old pause. Node's own coverage table hid this behind two more faults: it merges the test processes in the order it reads their records and the merge overwrites (40 orders of one run's records gave 10 files more than one result), and without source maps it lays the offsets of tsx's compiled code over the source text, so its lines were not the lines that ran; the command-line tests also ran tsx where it could not find `tsconfig.json`, so eleven screens were compiled two ways. The command-line tests now name the project's `tsconfig.json`, and `scripts/coverage.mjs` reads every process's record on its own, through the source maps, so the order cannot matter: three local runs gave the same number for every file, and removing one test file put eight files below their floors. The floors were set again from it; the mean line coverage reads 92.4% where Node's table said 96.6%, comments, blank lines and types no longer counting as lines.
- **The doctor itself.** Run by an agent, `doctor --fix` would have copied the build the agent was running into the protection (found while testing the repairs).
- **On a real machine, by the doctor.** The first `doctor` run on the author's machine found that Claude Code's Monitor tool, which runs a shell script, was not checked by the belt: its transcript check lists every tool that ran a command or wrote a file and is not checked. The same run had two false alarms of its own, now fixed: a session in the home folder counted the user's settings twice ("4 extra copies" of the hooks), and a hook program from an earlier build of the same version was called "changed after installation". The mod type-check now reads the tool list from Claude Code's own declarations and fails on a new tool that takes a command or a file path, wherever Claude Code has laid those declarations (on a developer's machine, in `npm run verify`); CI has no session to lay them, and there the doctor's transcript check stays the net.
- **The memory, while it was built.** `git remote get-url` answers with the address after `url.insteadOf` rewrote it, so the setup did not recognise a clone of the repository it had just named (it reads the configured `remote.origin.url` now); git's output, trimmed, had cut the first letter off the first uncommitted file of a handoff note; the engine's test kit listed no folders, so runs and handoff folders looked empty inside it (it lists them now, as a disk does). A live run in WSL2 answered from the old index: Claude Code had loaded it before the start's pull landed, so what a pull brings in is now told with the next prompt.
- **Sync and the memory kept by its owner, while they were built.** The doctor, run on the author's machine, called a memory folder set outside Mode_Code "one memory per project"; the memory setup, given a folder inside a larger repository for this computer only, would have started a git history of its own inside the other; the README still said nothing leaves your machine, though the memory went to GitHub. Mutation testing found checks the merge did twice (a value read back through the settings already refuses what they would correct), and they were removed.
- **The live stop case, against itself.** It judged a turn-back from the hook's stop record, which names the run after any stop, even the last one of a finished run: a session that never stopped early could pass. Turn-backs are counted from the session's stream now.
- **Full autonomy, in its first live run.** Every start in a real session was refused with the permission mode unknown: Claude Code runs the plugin's prompt hook before the safety-net hook's, and `SessionStart` carries no permission mode. The engine's test kit had put the mode on record before the prompt, which no real session does. The start now measures the mode at Claude's first step, and the kit records the hook's view beneath the plugin, after its prompt hook, so the order is part of every kit test.
- **`/0` opening the control center.** Before its tests were written, each way of opening a tab was run by hand with a probe program whose path holds a space (and in tmux a quote): a Windows Terminal tab and a PowerShell window on Windows 11, a window of tmux 3.4 in the WSL2 distribution; each ran in the session's folder, on a terminal, with its arguments exact. The engine's kit then failed in the WSL2 distribution, three of the new tests and one of the session controls that had failed there unnoticed since they came: a Windows path is not absolute on Linux, so the engine handed the kit's Windows world `/tmp/<test folder>/C:/Users/…`, which it never found; it drops everything up to the drive now. The probes ran outside Claude Code, and so missed what Claude Code adds: the first `/0` in a real session, opened in the home folder, failed, because Claude Code finds a program named without a path itself and refuses one found in Windows' app alias folder when the session's folder contains that folder (read in its process runner). A Bun of the same version (1.4.3) runs the alias by its full path, and sees it as a link that cannot be followed (`stat` is refused, `lstat` says link, a directory listing says link), so the plugin lists the folder instead of checking the file; the kit's world now has such links.
- **The session controls, in the author's own use.** Chat and manual chosen on the strip, then `terminal devam`, and the strip showed free and autonomous: continue still made a session autonomous and left chat, a rule from before the strip, which no test questioned because the tests had been written to it. The same session showed the note on its first prompt built before that prompt's own keyword, and a message from the session before, `terminal devam (<paste>)`, never seen as a keyword, so its handoff note went under the folder's name. Making `session.ts` a mutation target then found 19 changes no test noticed, in the parsing of state files, approvals and the live window, each with a test now.
- **Sessions closed without ending, reported by the author.** A new session was warned that two others worked in its folder; both had been closed minutes before, one of them seconds before (its end ran, but nothing marked it ended), the other closed with no end at all. The fix asks the session's process, so the lookup's answers were measured first on Windows 11 (`tasklist` for a running process, and the line it writes in place of one when there is none, in the system's language), and the live case checks in the real engine that the process the hook records is the session's own Claude Code. Writing that case found a gap of the fix's own: a session's change was kept only when its turn ended, so a window shut mid-turn would have owed no note; the first change of a turn is kept at once now.
- **An antivirus, against a test file, reported by the author.** Bitdefender quarantined `test/core/effects.test.ts` as `CMD:Heur.BZC.PZQ.Boxter` (its heuristic for malicious command scripts) at least 37 times in three days, every copy it saw: the mutation workers', a clone's in the temporary folder, and Claude Code's own backups of the file before an edit; the copy in the author's working folder was left alone. No single line was enough, and no other file in the repository or the package was taken. Together, a few sample commands read like an attacker's script: listing the running processes, asking for the Desktop folder, listing every file recursively by full path, writing into `%TEMP%`, `sudo rm -rf`. Someone who cloned the repository or downloaded its source would have been told a threat was found in a command-line tool they had just installed. Those samples now take the same paths through the classifier with neutral commands (mutation still catches 291 of 291 changes to the classifier and 14 of 14 to the mode guard), and L15 keeps it so: before the change it reported the file within ten seconds; after it, the file, three copies of it in one file, and every test file of sample commands joined into one were all left alone.

## Not covered

- **Branches an agent may not write a test for.** The doctor's checks for settings that turn hooks off are tested only with values that leave hooks on: the safety belt, rightly, refuses to let an agent write a settings fixture that turns hooks off. They are listed as `not-agent-testable` in `test/mutation-equivalents.json` and are for a person to cover.
- **Version comparisons the source never reaches.** Five comparisons of the installed version with this build's are skipped when running from source; the shipped-bundle tests reach them, mutation testing (which runs the source) does not.
- **Interactive Claude Code.** The two ways to approve a flow's plan (the plugin's dialog and Claude Code's plan dialog) were checked in real interactive sessions driven in an invisible console on 2026-10-13, not on every change. The live tests run `claude -p`. The permission dialog and the drawing of footer lines were checked in real interactive sessions by hand, not on every change, and so was `/00` (2026-10-14: keys typed into a real session in a new Windows Terminal window; idle and mid-answer, Claude Code, its shell and the window each ended); full autonomy's start window was checked the same way on 2026-10-15, in a pseudo console with this build loaded (`/full-auto` opened it, the task typed went into its field, Enter sent it with the keyword and the run started at the model's first step), while a press on the strip, a mouse click, was not; the kit stands in for Claude Code's exit and its turns; the resume after a quota reset is tested in the engine's test kit on a mocked clock, not in a session that waits for a real reset.
- **Terminals `/0` opens that no test machine has.** The arguments for iTerm2, the macOS Terminal, WezTerm, Konsole and GNOME Terminal are tested exactly, and their quoting against a real shell, but none of those terminals has opened the control center on a real machine yet: the macOS ones wait for the author's Mac.
- **A determined adversary on native Windows.** The belt is an accident preventer there, not a security boundary (see [safety-belt.md](safety-belt.md)).
